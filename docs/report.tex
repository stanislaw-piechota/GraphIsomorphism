\section{Using Generating Sets for Computing |Aut(G)|}

We have implemented the automorphism counting algorithms based on the permutation group techniques discussed in the course.
To compute the total number of automorphisms efficiently, our implementation finds a polynomial-sized generating set for the automorphism group, $Aut(G)$, rather than explicitly generating every single automorphism, which would not be computationally feasible for large graphs.

We created two variations of this counting mechanism, based on our two branching algorithms.
In both variations, we apply individualization refinement and continuously maintain a set of found generators.
To optimize the search space, we utilized the Pruning Lemma: whenever the search yields a trivial prescribed mapping, we safely prune the recursion tree and stop exploring that branch, as any further automorphisms discovered would already be accounted for in our generating set.

To handle the underlying group theory, we leveraged the provided utility code to compute orbits, transversals, and generating sets for stabilizer subgroups.
Building on these tools, we implemented algorithms for Order Computation, utilizing the Orbit-Stabilizer Theorem, and membership testing, utilizing recursive sifting to check if newly found automorphisms are already within the generated subgroup. % TODO: add souce for OST

The computation times on the sample instances are documented in Table~\ref{tab:aut_counting}.
As expected, applying this generator-based counting drastically reduces the computation time for large, highly symmetric graphs due to the heavily pruned recursion tree.
However, the mathematical operations required for order computation and membership testing introduce a noticeable overhead for smaller instances where explicit branching would otherwise be quick.

In all tested graphs, skipping membership testing led to a significant speedup, which either indicates that our implementation is not ideal or the graphs tested do not create enough redundant generators to slow down the order computation.

\subsection{Multithreading}
We noticed the standard program achieved at most 6-8\% CPU utilization on machines with 16 cores, which is a clear indication that the algorithm is not fully utilizing the available computational resources. To address this, we implemented a multithreaded version of our algorithm, allowing it to run concurrently across multiple CPU cores.
We experimented with different methods, first -threading- but found that it still didn't allow the python code to utilize more than one core, which is a known limitation.
To actually get it to utilize multiple cores, we switched to -concurrent- and used the ProcessPoolExecutor.
We tried to make branching itself spawn new processes, but even with this being limited to the first level of the search tree, the overhead of spawning processes and inter-process communication was too high, leading to worse performance than the single-threaded version.
Instead, we implemented a more coarse-grained parallelism approach, where graphs are compared to known isomorphic classes in parallel, the first match being returned and the rest of the comparisons being cancelled.
It still does add a couple seconds of overhead, but for a couple datasets it was the difference between solving the instance and timing out


In the pure Aut(G) tasks parallelism was used to run the automorphism counting algorithm for each graph in a separate process
